# VM-01 B1 — 파리 관절을 쓰는 최소 몸체 (설계·타당성 조사, 미구현)

id: VM01-B1 · status: design-only, 미구현(사용자 지시: "이번에는 설계/타당성
조사") · 2026-09-17 · 기준: `docs/tasks/VISUOMOTOR-PIVOT.md` B1 · 관련:
`docs/design/FLY-VISUAL-SPEC.md`(현재 순수 시각 오버레이), `envs/fly_visual.py`
(현재 mocap IK), `docs/design/VISION-01.md`·`docs/records/evidence/
VM01-vision-baseline.json`(§7에서 언급하는 V1과의 접점)

**이 문서는 설계만 담는다. 코드/XML 구현은 없다.** 현재 KC-01a/B1의 앞다리
(`envs/assets/fly_visual_front_legs.xml`)는 `mocap="true"` 바디로, **관절도
질량도 없는 순수 시각 IK 오버레이**다(`envs/fly_visual.py`의
`FrontLegGripOverlay`가 매 프레임 역기구학으로 위치만 지정) — "실제 앞다리
관절"이 아니다. 이 문서는 그것을 실제 물리 관절(질량·관성·구동력이 있는)로
바꾸는 설계를 다룬다.

## 1. 원본 NeuroMechFly rig 확인 (출처: flygym==1.2.1, Apache-2.0)

`docs/RESEARCH_SOURCES.md`가 이미 인용한 것과 같은 패키지(flygym==1.2.1)를
`pip download flygym==1.2.1 --no-deps`로 받아 원본(스트립 전) MJCF
(`flygym/data/mjcf/neuromechfly_seqik_kinorder_ypr.xml`)와 Python 소스
(`flygym/fly.py`, `flygym/preprogrammed.py`, `flygym/data/pose/
{pose_stretch,pose_tripod}.yaml`)를 직접 확인했다 — `scripts/
build_fly_visual_asset.py`가 이미 이 파일에서 "관절을 전부 제거"했다고
밝힌 바로 그 원본이다(I-08a-fix). 재현 명령은 그 스크립트 docstring과 동일.

### 1.1 앞다리 관절 구조 (확인된 사실)

`flygym.preprogrammed.all_leg_dofs`가 실제로 구동(position-control)하는
다리당 7개 자유도(원본 MJCF의 joint 태그로 직접 확인):

| 관절 | 축 | 역할 |
| --- | --- | --- |
| `Coxa_yaw` | 몸통 longitudinal | 다리 밑동 요 |
| `Coxa` | pitch | 다리 밑동 앞뒤 |
| `Coxa_roll` | roll | 다리 밑동 좌우 |
| `Femur` | pitch | 무릎 굽힘 |
| `Femur_roll` | roll | 넙다리 회전 |
| `Tibia` | pitch | 종아리 굽힘 |
| `Tarsus1` | pitch | 첫 발마디 굽힘 |

Tarsus2~5는 원본에도 자기 joint가 있지만 `all_leg_dofs`(구동 목록)에는
없다 — flygym 자신도 이들을 "능동 구동"하지 않고 `tarsus_stiffness=7.5,
tarsus_damping=1e-2`의 수동 스프링으로만 둔다(`flygym/fly.py` 기본값).
**즉 원본조차 "발끝까지 전부 능동 구동"이 아니다** — B1도 Tarsus1까지만
능동으로 두고 Tarsus2-5는 수동(스프링)으로 두는 것이 원본과 일치하는
설계다.

### 1.2 제어 방식 (확인된 사실)

기본 제어는 **위치(P) 제어**다(`flygym/fly.py` `control="position"`
기본값, `kp=45.0`, `forcerange=(-65,65)`, `ctrlrange=(-1e6,1e6)`,
`forcelimited=True`) — KC-01a의 `TorsoBatController`가 쓰는 방식(목표각 +
게인)과 같은 계열이며, KC-01a처럼 "최대 토크로 가속 후 PD로 정지"가 아니라
매 순간 목표각을 향한 순수 P제어다. 관절 자체 감쇠/강성은
`joint_damping=0.06, joint_stiffness=0.05`(구동 관절), 다리 접지에는 별도
**흡착(adhesion) 액추에이터**가 tarsal segment마다 있다(현실의 파리 발
흡착 기구를 반영한 원본 고유 기능 — 이번 최소 몸체가 접지를 요구하지
않는다면 켤 필요는 없지만, 존재 자체는 기록).

### 1.3 자연 관절범위 (확인된 사실, 참고용)

원본 raw MJCF에는 `<joint range=...>`가 **없다**(무제한 힌지) — flygym은
하드 한계 대신 포즈 데이터(`pose_stretch.yaml`/`pose_tripod.yaml`)로
"자연스러운" 각도를 관리한다. 두 포즈 파일에서 직접 읽은 실측 각도(도):

| 관절 | stretch(정지 자세) | tripod(보행 중 한 프레임) |
| --- | --- | --- |
| `LFCoxa`(pitch) | 19° | -0.79° |
| `LFFemur`(pitch) | -130° | -67.6° |
| `LFTibia`(pitch) | 0° | 43.4° |
| `LFCoxa_roll` | 0° | -1.4° |
| `LFCoxa_yaw` | 0° | 15.1° |

이 두 샘플만으로 "가동범위"를 확정할 수 없다 — **자연 관절범위는 이
두 포즈 사이 어딘가라는 참고 신호일 뿐**이며, 실제 B1 구현 시에는 더 많은
원본 포즈/궤적 데이터를 모아 통계적으로 정하거나, 원본이 그렇듯 하드
리밋 없이 자연스러운 범위를 벗어나면 "파생 공학 모델"로 표시하고 진행하는
두 방법 중 하나를 택해야 한다(§4).

### 1.4 미해결로 남기는 것: 질량/길이의 절대 단위

`<option gravity="0 0 -9810" .../>`와 "1mm 눈금자" 주석
(`flygym/arena/base.py`)은 **길이 단위가 mm**라는 강한 증거다(중력을
9.81 대신 9810으로 둔 것은 위치가 mm일 때 물리 단위를 맞추는 표준
트릭). 반면 **질량 단위는 확인하지 못했다** — raw XML의 `mass=` 속성을
전부 더하면 1.001(정규화된 "몸 전체=1.0" 규약처럼 보임)이지만, 이 MJCF를
실제로 mujoco에 로드해 컴파일한 뒤 `model.body_mass.sum()`을 읽으면
0.00026으로 **전혀 다른 값**이 나온다(컴파일러의 `boundmass`/관성 처리나
중복 정의된 파일이 자산 안에 있을 가능성 등, 원인을 이번에 확정하지
못했다). **이 불일치를 해결하지 않고 임의의 절대 질량(kg)·토크(N·m)
숫자를 만들어 쓰지 않는다** — 실제 구현 착수 전 이 단위 규약을 flygym
공식 문서/논문에서 확인하는 것이 선행 조건이다(`docs/RESEARCH_SOURCES.md`에
후속 기록 필요).

## 2. 현재 KC-01a 자산과의 척도 비교 (참고용 대조)

`envs/fly_visual.py`의 `FrontLegGripOverlay`(현재 순수 시각 IK)는
**현재 KC-01a 크기 척도에서** femur+tibia+tarsus1 합 도달거리
`TOTAL_REACH_M = 0.2821+0.2074+0.0902 = 0.580m`로 이미 캘리브레이션돼
있다(I-08a-fix, "UNIFORM SCALE" — 몸 전체가 같은 배율 K를 쓴다). 이는
**바로 그 앞다리 세 마디**를 이번 B1이 실제 관절로 바꿀 때 참고할 수 있는
"현재 척도에서의 목표 도달거리"다.

독립적으로, 원본 raw MJCF를 그대로 컴파일해 읽은 실측 앞다리 완전 신전
길이(Coxa~Tarsus5)는 몸통-머리 간 거리의 약 4.15배다(2.153 raw 단위 /
0.519 raw 단위). 이 비율을 현재 KC-01a의 머리-몸통 축 거리(0.2326m,
`docs/design/VISION-01.md` §3 실측)에 곱하면 ~0.97m로, 위 0.580m와 같은
자릿수이지만 정확히 일치하지는 않는다(다른 기준축이므로 정밀 일치를
기대하지 않는다 — 두 숫자 모두 "대략 수십cm~1m 규모"라는 것만 교차
확인용으로 쓴다).

**결론(§4 방향 결정의 근거)**: 앞다리 관절에 실제 물리를 넣을 때
`TOTAL_REACH_M=0.580m`(이미 이 리포의 시각 파이프라인이 쓰고 있는 값)를
1차 목표 도달거리로 채택한다 — 새 척도를 발명하지 않고 기존에 검증된
값을 재사용한다.

## 3. 공·도구 크기를 몸에 맞춘다 (사용자 지시, "원 스케일 우선")

현재 KC-01a 공은 지름 0.0732m(정식 야구공)이다. §2의 0.580m 도달거리
기준으로 보면 공 지름/도달거리 비율 = 0.0732/0.580 ≈ 0.126 — 손 도달거리의
약 8분의 1인 물체로, **몸 크기 대비 이미 상당히 크다**(실제 파리에게
정식 야구공은 몸 전체보다 훨씬 클 것이므로, 이 비율만으로도 "지금 크기
그대로는 원 스케일 파리에게 무리한 과제"라는 것이 드러난다 — §1.4에서
정확한 절대 길이 비율은 못 정했지만, 상대 비율만으로도 결론은 나온다).

**설계 결정**: 이번 B1은 정식 야구공을 그대로 쓰지 않는다. 공 지름은
도달거리의 10~20%(0.058~0.116m) 범위에서 시작하고, 도구(타격면)는 그
공을 칠 수 있는 최소 크기(막대/패들 형태, 길이는 도달거리 이내)로 둔다.
사용자가 언급한 "크고 느린 공"(다음 학습 단계의 시작점)은 **이 축소된
스케일 위에서의 "크고 느림"**이지, 정식 야구공 스케일을 뜻하지 않는다 —
두 스케일을 섞지 않는다. 확대가 필요해지면(예: 도달거리를 인위적으로
키우는 경우) §1.4의 질량/관성/토크/시간 스케일 재계산이 먼저 필요하다는
것을 여기 명시해 둔다(이번에는 확대하지 않는다 — §2의 기존 척도를
그대로 쓴다).

## 4. 인간식 직립·고정 스윙을 강제하지 않는다

KC-01a/B1의 "옆선 타자 자세"는 **캐릭터 외형(시각) 규약**이지 과학적 몸
모델이 아니다(`docs/design/FLY-VISUAL-SPEC.md`). B1은 이 자세를 필수로
가져오지 않는다:

- **몸통 지지**: 최소 목표는 "몸통을 지지한 상태에서" 앞다리로 도구를
  움직이는 것이다 — 몸통 자체의 자세(수평/수직/기울기)는 이번 설계의
  자유 변수로 남긴다. 인간처럼 수직으로 서 있어야 한다는 요구는 없다.
- **중간/뒷다리**: 이번 최소 몸체는 이들의 실제 지지 여부를 명시적으로
  결정해야 한다(§5의 세 후보 모두에서). 제안: 중간/뒷다리는 원본
  `pose_stretch` 자세로 고정하되, "접지·체중 지지"는 하지 않는 것으로
  명시한다(몸통 자체가 지지되므로) — 이는 실제 파리 자세의 근사가
  아니라 이번 범위(전신 균형 미착수)에 맞춘 **파생 공학적 단순화**임을
  표로 표시한다(§5).
- **스윙 순서**: KC-01a의 "몸통 선행→팔 가속" 같은 특정 순서를 정답으로
  강제하지 않는다 — 이는 VM-01의 명시적 목표(§목표: "인간식 몸통
  선행·동방향 회전·고정 스윙 변위·팔로우스루를 정답 동작으로 강제하지
  않는다")와 일치시키는 것이다. 어떻게 움직여 공을 치는지는 이후 학습
  정책이 찾는다(`docs/tasks/VISUOMOTOR-PIVOT.md` "이후 순서").
- 자연 관절범위(§1.3)를 넘는 목표각을 설계에 쓸 경우 반드시 "파생 공학
  모델(자연 범위 초과)"로 표시한다 — 몰래 자연스러운 척 하지 않는다.

## 5. 최소 구현안 비교 (설계 비교, 구현은 다음 단계)

| 후보 | 구성 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 한 앞다리 + 도구 부착**(제안) | 지지된 몸통 + 앞다리 1개(7DOF, §1.1) 끝에 도구 고정 부착(그립 폐루프 없음) | 양손 협응이라는 불필요한 초기 병목을 피한다(사용자 지시와 일치) — 자유도 7개만 학습/제어하면 됨, 디버깅 단순 | 실제 파리의 "두 앞다리로 잡기"와는 다르다 — 도구가 몸에 고정 부착된 것에 더 가까운 근사 |
| B. 두 앞다리 그립 | 앞다리 2개(14DOF) + 그립 폐루프 제약(현재 `FrontLegGripOverlay`의 물리 버전) | 실제 그립 역학(양손 협응)을 다룸, 현재 시각 자산과 자세 일치 | 폐루프 제약 자체가 새로운 난제(두 다리가 같은 도구를 놓치지 않아야 함) — 이번 단계엔 과함 |
| C. 지지된 몸통만 + 도구를 몸통에 직접 부착(다리 없음) | 다리 없이 몸통에 도구 고정 | 가장 단순 | "앞다리 관절로 움직인다"는 최소 목표 자체를 만족 못함 — 이번 과제 요구와 불일치, 채택 안 함 |

**제안: 후보 A(한 앞다리 부착)**를 다음 단계의 실제 구현 대상으로
문서화한다 — 실제 구현 여부/선택은 이 문서가 확정하지 않고, 사용자 승인
후 별도 작업으로 진행한다(이번 범위는 설계까지).

## 7. 도달성·출력·시각 가시성 예산

- **도달성**: §2의 `TOTAL_REACH_M=0.580m`를 도구 길이 포함 최대 도달거리
  예산으로 쓴다 — §3에서 정한 공 지름(0.058~0.116m)이 이 예산 안에서
  타격 가능해야 한다(도구 자체 길이를 얼마나 쓸지에 따라 유효 스윙
  반경이 달라짐 — 이번엔 도구 길이를 확정하지 않는다).
- **출력**: §1.4의 절대 토크 단위를 확정하지 못했으므로 이번 설계는
  출력 예산을 숫자로 고정하지 않는다 — gear/토크 결정은 §1.4 해결 후
  별도 캘리브레이션(KC-01a가 했던 것과 같은 방식의 무공 스윕)이
  필요하다고만 명시한다.
- **시각 가시성**: V1(`docs/design/VISION-01.md`, 이번 갱신의 실측
  `docs/records/evidence/VM01-vision-baseline.json`)이 이미 "공은 대부분
  비행 구간에서 서브픽셀"이라는 것을 실측했다 — B1의 공이 §3처럼 더
  작아지면 가시성 문제는 **더 심해질 수 있다**(각크기는 물체 지름에
  비례하므로, 지름을 줄이면 같은 거리에서 각크기도 줄어든다). 실제 B1
  스케일에서의 픽셀 크기 재계산은 몸체 구현 후 V1 파이프라인을 재적용해
  확인해야 한다(이번엔 하지 않음, 다음 단계).

## 8. 남은 미해결 항목 (다음 단계 전 필요)

1. §1.4의 질량/길이 절대 단위 규약 확정(flygym 문서/논문 확인) — 이것
   없이는 실제 토크/에너지 계산이 근거 있는 숫자가 아니다.
2. 자연 관절범위(§1.3)를 더 많은 포즈/궤적 샘플로 통계화하거나, 하드
   리밋 없이 진행할지 결정.

   §목표의 "무공 관절 구동... 검증"), 시각·접촉 통합.
